# MODEL_CHOICE — выбор LLM, стоимость, латентность, гиперпараметры

Числа токенов и латентности — из реального прогона `evals.run_all` ([EVALS.md](EVALS.md), 2026-09-24). Цены — с официальной страницы OpenAI (`developers.openai.com/api/docs/pricing`, Standard, проверено 2026-09-24); цены меняются, перед защитой их стоит сверить. Стоимость ниже — **арифметика по измеренным токенам**, а не счёт из биллинга.

## 1. Какая модель используется и почему

| Роль | Модель | Почему |
|---|---|---|
| Извлечение процесса (PDF-текст → ProcessSpec), Vision (PNG/JPG), рекомендации | `gpt-4o-mini` | 1) **Одна модель на текст и изображения** — один SDK, один формат Structured Outputs, нет отдельного OCR-стека. 2) **Structured Outputs** (`chat.completions.parse`) гарантирует ответ в схеме Pydantic — на этом построена программная валидация. 3) **Цена и скорость** (см. ниже) позволяют прогонять 30-примерные оценки многократно. 4) Модель задана условием проекта (GPT-4o-mini Vision) |
| Эмбеддинги RAG | `text-embedding-3-small` | $0.02 за 1M токенов; база из 14 паттернов и запросы — короткие русскоязычные тексты; Hit@3 = 19/23 (83%) уже на ней. Более крупную модель не пробовали |

**Что не проверялось (честно):** Claude, Gemini, локальные модели и другие модели OpenAI (`gpt-4o`, `gpt-4.1-mini`) **на этой задаче не сравнивались**. Довод «почему GPT, а не Claude/Gemini/локальная» — практический, а не экспериментальный: требование проекта, готовая поддержка Structured Outputs и Vision, цена, отсутствие инфраструктуры для локальной модели. Что дала бы более сильная модель, неизвестно; гипотеза (не проверена): она реже предлагала бы автоматизацию там, где она не обоснована (отрицательные примеры), но стоила бы кратно дороже.

## 2. Стоимость, латентность, качество

Измерено на Golden Dataset (30 примеров, конфигурация B — с RAG, средние на один вызов анализа):

| Показатель | A: без RAG | B: с RAG (рабочая) |
|---|---|---|
| Токены prompt / completion | 6334 / 377 | 8341 / 520 |
| Латентность LLM (среднее / p95) | 5.14 / 8.16 с | 7.01 / 10.28 с |
| Сквозная латентность (поиск + LLM), среднее | 5.14 с | 8.11 с |
| Recommendation F1 (macro, по смыслу) | 0.696 | 0.725 |

**Стоимость одного анализа (только вызов рекомендаций, gpt-4o-mini: $0.15 / 1M вход, $0.60 / 1M выход):**

| Конфигурация | Расчёт | Стоимость |
|---|---|---|
| A | 6334·0.15/1e6 + 377·0.60/1e6 | ≈ $0.0012 |
| **B (рабочая)** | 8341·0.15/1e6 + 520·0.60/1e6 | **≈ $0.0016** |
| Эмбеддинги запросов в B | ≈ 211 токенов · $0.02/1e6 | ≈ $0.000004 (пренебрежимо) |
| Весь A/B-прогон B на 30 примерах | | ≈ $0.047 (A: ≈ $0.035) |
| 1000 анализов в конфигурации B | | ≈ $1.56 |

Для сравнения — та же нагрузка по токенам на других моделях (**расчёт, не измерение**: качество и число токенов у них были бы другими): `gpt-4.1-mini` ≈ $0.0042 (×2.7), `gpt-4o` ≈ $0.026 (×17).

**Не входит в расчёт:** вызов извлечения процесса из PDF/изображения (токены при извлечении не замерялись; изображение тарифицируется по своим правилам) и кэш промптов (не использовался).

**Баланс стоимости, латентности и качества.** Разница A → B: +$0.0004 на запрос, +2.97 с, +2007 токенов prompt, при этом F1 не вырос устойчиво (два прогона: −0.014 и +0.029, оба в пределах шума). Оправдание RAG — не точность, а **прослеживаемость**: ссылка на паттерн и разбор условий применимости у 100% рекомендаций (у A — 0%). Если бы требовалась только точность, по данным выше выгоднее конфигурация A; для продукта, где рекомендацию нужно объяснить пользователю, выбрана B. Это осознанный компромисс, а не победа RAG по метрике. Стоимость в ~$0.002 за анализ — не ограничивающий фактор; ограничивает скорее латентность (≈ 8 с сквозная) и недетерминизм ответов.

## 3. Гиперпараметры

| Параметр | Значение | Основание |
|---|---|---|
| `temperature` | 0.0 | **Эксперимент** (6 примеров × {0.0, 0.7} × 3 seed) с правилом, заданным заранее: более высокая температура выбирается только при приросте F1 ≥ 0.05 без ухудшения устойчивости и доли нарушений. В последнем прогоне F1 при 0.7 не выше (0.622 против 0.644, −0.022) и устойчивость между повторами ниже (0.667 против 0.741) → выбрано 0.0. В предыдущем прогоне того же эксперимента F1 при 0.7 был выше (+0.122) — знак разницы меняется от прогона к прогону, значит, эффект на 6 примерах × 3 повтора неотличим от шума; решение опирается на воспроизводимость, а не на измеренный выигрыш |
| `top_p` | 1.0 | **Не варьировался** (значение по умолчанию API). Экспериментального обоснования нет; при `temperature = 0` влияние `top_p` малó |
| `max_tokens` | 4096 | Наибольший наблюдавшийся ответ — 809 токенов (в предыдущем прогоне 881); лимит ни разу не достигался. Это защитный потолок, а не оптимизированное значение; экспериментов с меньшими значениями не было |
| `seed` | 42 (оценки) | воспроизводимость по возможности; API не гарантирует побитовую повторяемость |

Значения — в `processmind/config.py` (`LLM_TEMPERATURE`, `LLM_TOP_P`, `LLM_MAX_TOKENS`), переопределяются в `.env`.

## 4. Что будет, если основная LLM недоступна или подорожает

**Реализовано:** ошибка LLM не роняет приложение — анализ завершается исходом `failed` с текстом причины, успех не имитируется; ошибка видна в интерфейсе и (при включённом LangSmith) в трейсе.

**Не реализовано:** автоматического переключения на резервную модель (fallback), бюджетных лимитов и кэширования ответов в продукте нет. Как это можно сделать (план, не код): второй провайдер за тем же интерфейсом `request_structured_ex` с переключением по типу ошибки (таймаут, 429, 5xx); кэш по хэшу (процесс, версия Skill, версия базы знаний, параметры); лимит токенов на анализ. Из-за того что вызовы LLM собраны в одном модуле (`processmind/parsing/llm.py`), замена или добавление провайдера локализованы в нём — но Structured Outputs и Vision в этом модуле специфичны для OpenAI, поэтому переход на другого провайдера потребует переписать эти вызовы, а не только сменить имя модели.
